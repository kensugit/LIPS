# LIPSの展開調整

取引先対応、PDF、一括取込、自由文AI検索は同じDell LIPS Webを更新する。コード作成と隔離テストは並行できるが、ポート5987の受信と本番切替は直列にする。これは将来の個別展開への包括承認ではない。

## 作業の順序

1. 最新inspectと調整記録を確認し、他担当へ担当範囲と次の切替を連絡する。
2. その本番版に一致するクリーンなソースから派生する。自分の変更だけでなく、既存の取引先・一括取込・ファイル選択・PDF・AI機能を保持する。
3. 同じ修正が既に採用済みなら、コードと契約を比較して重複展開を省く。別版を自分の期待版に見せるためガード値だけを変更しない。
4. 受信または切替前に共通調整ツールで予約する。所有者以外は開始しない。予約期限を過ぎても自動取得・強制解除しない。所有者の操作記録、受信位置、cleanupと本番版を照合して解消する。
5. 本番切替直前にもinspectを照合する。別担当の変更が入れば候補を止め、その変更を統合してテスト・パッケージを作り直す。
6. 相互TLS一括転送、固定コマンド、ハッシュ検証、バックアップ、復旧、稼働版確認を既存手順どおり実施する。通信結果が不明なら再送・再適用しない。
7. 検証結果と未完了事項を引き渡し、所有者が予約を解放する。次担当は自分でも最新inspectと引渡しを照合する。

## 引渡しに含めるもの

- 担当セッション、operation ID、引渡し先と受領状況。
- current package、source commit、Web/DB image、schema fingerprint。
- 検証済みクリーンソースの絶対パスとGit状態。
- AI有効/無効、sidecarの有無と共有ネットワーク状態。未確認は未確認として残す。
- 変更概要、回帰試験、本番受入、バックアップ、受信ファイルのサイズ/SHA、cleanup。
- 不明な操作・残作業・次に許可されている工程。

商品データの取込完了、Webの配置完了、実運用の受入は分けて記録する。業務取込が他担当で実行中なら、そのデータを過去バックアップへ戻したり、自分の旧検証件数へ合わせたりしない。

## AI接続を保持する場合

AI有効後のllm-linkはWebのネットワーク名前空間を共有する。Webを作り直したときは、レビュー済みの構成でllm-linkも同時に作り直し、新しいWebへ接続する。Web-onlyの固定ヘルパーに第三サービスや秘密を渡す迂回はしない。AI無効のWeb更新と、接続設定・AI有効化は分離する。

新しいWeb版が出たら、Composeの保護された再取得と最新の運用入力・consumerの検証を行う。旧packageやcontainer IDを残した証明は流用しない。固定SHAだけを書き換えて証明を更新したことにしない。

## 調整ツールの位置付け

`tools/release-coordination` のローカル予約は、同じ共有作業領域を使う担当間の協調を支援する。既存の本番側ロック・期待版ガードを置き換えず、別PCやこの手順を利用しない操作まで強制的に排除するものではない。全担当への通知、受領回答、予約、本番側の検証をそれぞれ記録する。

### 準備を止めないための依存分離（2026-10-30）

- 共有資源を使わないソース照合、静的レビュー、操作案作成、保存済み証跡の確認は並行する。これらに受信枠の取得・引渡しや、別案件の実行完了を要求しない。
- 上記の排他不要な準備には共通の実行時間枠を適用しない。実機転送・限定診断・推論の認可期間や、同じ資源を変更する実操作の時間調整は別に維持する。
- PGの準備はLIPS b252の転送・取込完了、自由文LLM受入、Qwen受入を前提にしない。LIPSの準備にもPG-Bの実行完了を要求しない。過去の「b252先行」は実操作の順序調整の記録であり、全準備の停止条件へ拡張しない。
- 実受信・受信module変更・本番切替の前には、今回触れる同じ資源の現状態、実owner、未完了operation、cleanup、対象版を確認する。別案件の完了ではなく、競合する資源の証拠で可否を判断する。
- 未開始の候補に存在しない受信完了receiptを要求しない。ただし、保存証拠にoperationが見つからないことを、現在の受信停止・予約不在の証明にしない。現在未観測ならUnknownを保持し、必要な限定読取を具体化する。
- 調整上の待ち条件を除くことは、予約・mutation.lock・固定コマンド・認証・SQL安全条件の解除ではない。期限切れや過去の解放記録を根拠に実枠を強制解除しない。

## Dellでの本人操作を減らす（2026-10-17本人指示）

### 修正版の共有承認の引継ぎ（2026-10-30本人方針）

- ウサギマスター経由の本人回答「承認済みのもととなるファイルの修正版の共有は自動的に共有承認を引き継いで処理してください」に従い、同じ宛先・目的・範囲・機密性・権限を保つ修正版の共有は、既存承認を引き継ぐ。旧版は保持し、新版の原本・サイズ・SHAを固定して照合する。
- 宛先追加、目的・範囲・機密性・権限の変更には新しい確認が必要。共有承認の引継ぎは、本体起動、実機搬入、推論、本番変更、DB保存や、単回と指定された試験の自動再実行を承認するものではない。
- 今回の搬入proposal r4は、同じ非公開Space・既存LIPS主とARKへの3原本共有、架空receiptによる非通信PS5.1/7各1回と独立レビューの指示を別途受領。実試験結果は各engineの版・起動記録・原本SHAと結び付け、出力ファイル名だけで実engineを判定しない。

- 担当側で可能な候補生成、静的検査、模擬試験、他担当との照合を先に完了し、同じ承認・前提の下で連続実行できる処理は一つの起動手順へまとめる。
- 案内は実行するPC、管理者の要否、シェル、使用する一つの最新版ファイルを明示する。既に提示した手順の結果待ち中に、同じ操作の別版を重ねて依頼しない。
- PowerShell 5.1の新しい子プロセスを起動し、再貼付やエンジン読込済みエラーを防ぐ。結果はDownloadsの新規JSONへ自動保存し、画面バッファ全体のコピーを要求しない。
- 成否、工程、停止理由、実施済み処理、受信ファイルのサイズ/SHA、cleanupと確認できた現在状態を、秘密を含めず一つの結果へまとめる。秘密鍵、完全Compose、資格情報、非公開stderrは返却対象にしない。
- 正常終了した工程は保存済み結果を照合して引き継ぐ。結果不明時は読み取り診断をまとめ、送信・適用・鍵生成を自動で再実行しない。
- 最新factsの親レビュー、受信窓と送信側の同期、BASEとDellの操作境界など、実際に依存する箇所だけを人の操作区切りにする。操作削減を理由に承認範囲や既存の権限・転送・本番ガードを拡張しない。
