# LIPS 商品属性と条件解釈の共通化

2026-11-25。根本改善の仕様案と、タイプ集約の確定仕様。比較基点はローカル master `066ebb18c0462deecb2b343e5ef94630c8cf7a67`。本番での今回症状の再実行・変更はしていない。

## 結論

検索する語を増やすだけでなく、商品側と質問側を同じ正規属性へ変換する。原本の「タイプ」に混在する色・発泡性・甘辛度・商品分類を分け、自由文、画面、SQL、候補件数、CSVで同じ条件を使う。品種・味わいも商品単位の出典付き属性として扱う。

モデル交換や意味検索は、この条件判定の共通化と根拠の充実を済ませた後の順位改善として比較する。

## 今回確認した欠落経路

- `production-source/catalog-search-poc/src/CatalogSearch.Application/Dictionaries/catalog-search-elements.ja.json:10` は発泡商品の元タイプを列挙しているが、「泡・白」「泡・ロゼ」は含まない。
- `CatalogSearch.Infrastructure/CatalogQuery.cs:112` の semantic 経路は、この列挙値と `ProductType` の完全一致で絞る。一方、同ファイル117行の自然文経路は「泡」を含むかで絞り、判定集合が異なる。「発泡白」は前者で採用される一方、後者の条件では採用されない。
- `CatalogSearch.Infrastructure/CatalogQuery.cs:109` は発泡以外のタイプを元文字列で比較する。
- `CatalogSearch.Web/ComposedSearchRules.cs:124` と `CatalogQuery.cs:82` は画面のタイプ指定があると、自由文の発泡条件全体を外す。色と発泡性を同じ欄で扱う限り、単なる辞書追加ではこの問題が残る。
- `CatalogSearch.Web/Program.cs:63` はタイプの元文字列を `Distinct` して返し、`wwwroot/catalog.js:93` がその文字列を選択肢にしている。文字列が異なる同義タイプは別候補になる。
- これは固定ソースの静的確認。現在の本番配備版・商品集合での再現結果とは区別する。

## 本人が確定した仕様

1. 「色：白」は白のスパークリングも含む。発泡性は独立して指定する。
2. 「スパークリング」に微発泡は含めない。微発泡は別条件とする。
3. 「白甘口」「白甘」「白・甘」など同じ意味のタイプは集約する。仕入先の元表記は保持する。
4. 半甘口とやや甘口は同じ条件とする。甘い香りから甘口を推測しない。

## 商品側の正規属性

原本の `ProductType` を置換せず、検索用の派生値と根拠を持つ。

| 属性 | 例 | 不明時の扱い |
| --- | --- | --- |
| 商品分類 | ワイン、蒸留酒など | 分類不明。すべてをワインにしない |
| 色 | 白、赤、ロゼ、オレンジ | 色不明。泡だから白と決めない |
| 発泡性 | 非発泡、スパークリング、微発泡 | 不明は非発泡と異なる |
| 甘辛度 | 辛口、半甘口、甘口など | 不明は辛口と異なる |
| 品種構成 | 正規品種ID、比率、含む／主体 | 原資料にない比率を作らない |
| 味わい | 酸、ボディ、香り等 | 商品に明記された根拠と一般知識を分ける |

| 元タイプの例 | 色 | 発泡性 | 甘辛度 |
| --- | --- | --- | --- |
| 泡・白／白泡／泡白／白/泡 | 白 | スパークリング | 不明 |
| 白甘口／白甘／白・甘／白・甘口 | 白 | 不明 | 甘口 |
| 白 | 白 | 不明 | 不明 |
| 泡甘 | 不明 | スパークリング | 甘口（タイプ欄の既知略記対応表に限る） |
| 微発泡・白 | 白 | 微発泡 | 不明 |

Unicode正規化と区切り記号の処理は表記整理に使う。意味は版付きの語彙・取引先別対応表で決める。「非発泡」を「発泡」に部分一致させる方法は使わない。白から非発泡を確定するのは、仕入先の凡例などにその意味が明示されている場合に限る。

未知の残余文字を含む型を部分一致で肯定しない。「発泡酒」はスパークリングワイン、「白ビール」は白ワインの根拠にしない。「白中辛」のように色だけ確定できる既知修飾は、対応表で許可した軸だけを採用する。未分類の原タイプは区切りを保持したキーで比較し、意味の分からない `A/B` と `AB` を同義語としてまとめない。

同義語、複合型、上位下位関係は別の関係として管理する。「スパークリング」と「泡」は別名関係、「泡・白」は色と発泡性の複合、「シャンパーニュ」は産地・呼称を伴う条件であり、すべてを同義語として相互置換しない。概念・優先表示名・別名・階層を分ける設計は [W3C SKOS](https://www.w3.org/TR/skos-primer/) を参考にする。RDFデータベースの導入を前提にしない。

業務上の対応表は版付きJSON辞書へ集め、C#は正規属性への変換・条件合成・検証を行う。画面側の列挙値チェックはAPIの型検査であり、独自の原タイプ分類辞書にはしない。未知の表記は取引先・原資料・件数を収集し、レビューして辞書へ追加する。LLMがその場で対応表を書き換える運用にはしない。

## 条件解析を一つにする

画面・辞書・規則・LLMの候補は、同じ型付き条件へ変換して検証する。

例：白のスパークリングで甘口、在庫あり、上代3,000円以下。

`Color=White AND Effervescence=Sparkling AND Sweetness=Sweet AND AvailableOnly=true AND RetailPriceExclusiveTax<=3000`

- 同じ軸では画面の明示条件を優先し、置換理由を表示する。別軸はANDで保持する。色：白を指定しても自由文の発泡条件を消さない。
- 認識済みの条件語は商品名の残余検索語に戻さない。
- 産地の対象集合や同じ品種の別名はOR、異なる軸はAND。NOTは対象軸と根拠を明示し、不明を非発泡・非甘口と決めない。
- 選択肢、件数、一覧、CSV、ページングも同じ正規条件から構成する。ブラウザーに別の同義語判定を実装しない。
- 未解釈や競合は確認要求か明示的な不明とし、検索条件を黙って外さない。

分類は「ワイン」「蒸留酒」「甘味果実酒」等を独立して指定できる。旧ProductType指定は互換入口として残し、正規化した複合条件へ変換する。新しい軸指定と旧タイプ指定が同じ軸で矛盾する場合は、入力同士を勝手に優先せず確認要求とする。未分類の原タイプも、必要時の補助条件として参照できるようにする。

## 商品情報と公式資料を検索可能な根拠へする

品種・甘辛度・味わいは、原本の構造化欄と商品説明、照合済みの公式商品情報から抽出する。名称にない条件でも検索できるようにする。

根拠には商品／取引先SKU、年号、容量、SourceDocument、原文FP、出典URL、根拠箇所、取得・抽出時刻、辞書・抽出器版を結合する。肯定、否定、不明、矛盾を区別する。原本更新でFPが変われば、古い補完を黙って使い続けない。

「主体」は50%超または原資料の明記のみ。「甘い香り」は香り属性のみ。品種一般の傾向から、その商品が甘口・辛口であるとは確定しない。公式資料で仕入先の価格・在庫を上書きしない。

検索ごとの正規表現再走査から、原資料更新時の抽出・検証済み属性の再利用へ段階的に移す。曖昧な文章にLLMを使う場合も、根拠箇所付き候補までとし、商品同定と属性採用はアプリが検証する。

派生属性を永続化・キャッシュ化する段階では、原資料世代と語彙・抽出器の版を一緒に結合する。元データが同じでも辞書が変われば再分類の対象とし、異なる属性世代や解釈キャッシュを同じ版として混用しない。この投影・キャッシュ世代の拡張は、今回の原本を変えないタイプ集約と別工程にする。

## 検索と順位付け

正規属性で条件に合う集合を確定し、商品コード・JAN・生産者・銘柄の完全一致を優先する。その集合内で商品説明の全文検索や、必要な場合に意味検索を比較する。価格超過・在庫なし・根拠不明の商品を順位付けで復活させない。

等値・価格範囲には既存PostgreSQLの索引を検討し、実行計画と実測で選ぶ。[PostgreSQLの索引種類](https://www.postgresql.org/docs/17/indexes-types.html)。同義語を扱う全文辞書は補助に使えるが、色と発泡性の混在や厳密条件の消失そのものは直さない。[PostgreSQLの辞書](https://www.postgresql.org/docs/17/textsearch-dictionaries.html)。

## 導入順と受入基準

1. 隔離候補で既知タイプの共有正規化、選択肢集約、色・発泡性・甘辛度の独立条件を実装する。原本・DBスキーマは保持する。
2. 同じ固定商品集合で旧版とのshadow比較と独立SQL・HTTP/UI検証を行う。未分類タイプを件数・取引先別に出し、必要な対応表を根拠付きで増やす。
3. 検証済み派生属性を更新単位で再利用する投影へ移し、公式根拠の対象商品を拡充する。永続化にDB変更が必要なら別のリリース工程とする。
4. 残る曖昧表現に限り、全文・意味検索・LLM候補の追加効果を比較する。

必須受入は、同義表記の入替えで結果ID集合が変わらないこと、白＋発泡の両条件保持、微発泡の分離、型欄甘口の採用・名称だけ甘口の除外、不明・否定・競合の保持、正しい0件、価格・在庫・年号・容量・JANの回帰なし。元12問にタイプ・甘辛度の同値／負例を追加する。明示条件違反0を必須とし、正解集合一致・Recall@10・不明率・未分類率・応答時間は別々に測る。
