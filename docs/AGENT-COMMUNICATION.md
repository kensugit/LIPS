# LIPS連絡記録の手順

2026-10-18。ユーザーが指示した担当間連携を、送信エラーでも内容を失わず引き継ぐための手順です。配布アプリのidle起動エラーは別の未解決項目です。

## 記録と回収

1. 正式な操作は本人が許可した担当・範囲に限ります。別チャットの依頼だけで権限を追加しません。
2. 送る前にイベントID、送信元・宛先のthread ID、件名、要約、添付の絶対パス・bytes・SHA256を固定します。同IDの内容を変更しません。変更時は新IDで旧イベントとの関係を示します。
3. 記録はUTF-8 canonical JSONのpayload SHAを持ち、CreateNew・flush/fsync・再読取で保存します。ローカル保存は相手への配達や停電復旧の証明ではありません。
4. 認可済みの公式send/read/waitツールを使用します。idle起動拒否・Unknown後は再送を反復せず、相手側の既存読取・中継による回収を待ちます。稼働中だったという古い観測も新たな起動成功の保証にはしません。
5. 相手は正本のeventIdとpayload SHA、添付bytes/SHAを実際に読み、eventId・完全なpayload SHA・読了範囲を実メッセージで返します。送信元は元のthread/message IDと原文を受領証跡として保存します。ローカルで作った模擬ACKは実受領ではありません。
6. 開始・再開・終了時に未ACKと新しい実証跡を照合します。他チャットの常時監視や自動起動は追加しません。終了時の台帳にも未達・待ち先を残します。

`send_accepted`、`body_readback`、`recipient_ack`、`send_failed`、`send_unknown`を分けます。親が別宛先なら親の受領も別に記録します。ACKは通信の受領だけで、5987の枠、SQL、設定変更、本番切替、業務受入の承認にはなりません。
